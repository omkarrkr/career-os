# M2 auth schema proposal — not deployed

Prepared 23 November 2026. These files are deliberately outside `prisma/migrations` and are not the active Prisma schema. No automatic migration command applies this directory. Do not execute the SQL against Supabase yet.

## Files and review

- `schema.prisma`: proposed Goal ownership, User, AuthSession and RefreshToken models. It intentionally has no runtime client generator.
- `migration.sql`: SQL generated by the installed Prisma 7.10.0 schema-to-schema diff, reviewed and wrapped in BEGIN/COMMIT. It adds tables, a nullable ownership column, uniqueness constraints, indexes and restrictive foreign keys. There are no row updates/deletes or drops.
- `../../schema.prisma`: unchanged active schema. The running API/client continue to use it and do not expect undeployed columns.

Generator command from backend (writes a new review file; not an apply command):

```powershell
.\node_modules\.bin\prisma.cmd migrate diff --from-schema prisma/schema.prisma --to-schema prisma/proposals/auth/schema.prisma --script --output prisma/proposals/auth/migration.sql --config prisma7.config.ts
```

This compares local datamodels, not the remote datasource. Regeneration overwrites the draft's transaction wrapper/comment; review the SQL and restore the wrapper before considering it ready. No client generation is performed from the proposal.

## Proposed database rules

- Goal.userId is nullable and has no default owner, preserving legacy goals unassigned.
- User.email is unique. Application code must normalize email before writing; this plain-text unique index is not independently case-insensitive.
- RefreshToken.tokenHash is unique; only hashed high-entropy tokens will be stored by future auth code.
- Every non-null owner/session reference must point to a real parent. ON DELETE RESTRICT prevents automatic cascaded loss. ON UPDATE CASCADE maintains references if an identifier changes.
- Ownership and session references are indexed.
- Prisma generates UUID defaults and updatedAt values at the client level; the SQL does not give those fields database defaults. Direct-SQL tests supply them explicitly. The schema alone does not enforce password hashing, safe public responses, session validity, token entropy or authorization; application code must implement these.

## Isolated checks

```powershell
Set-Location C:\PROJECTS\career-os\backend
npm.cmd run prisma:validate:auth-proposal
npm.cmd run test:migration:auth
```

Tests apply the original migration and this proposal to an in-memory PGlite PostgreSQL engine with fictional data. They verify preserved legacy values/NULL owners, empty new tables, unique email/token hashes, valid foreign keys, restricted deletion, ownership indexes and rollback on a simulated later SQL failure. No URL is used, no Supabase rows are queried and no persistent test database is created.

PGlite is an embedded PostgreSQL build, not the deployed Supabase server. These checks do not establish target server version/permissions/extensions, operational locking impact, Prisma-client integration, live drift, backup/restore readiness or safe live backfill. Additional target-compatible staging verification is required before remote application.
